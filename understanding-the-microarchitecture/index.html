Let’s think about the following ARM assembly program.

0x10000	mov x0, #0x1234
0x10004	mov x1, #0x5678
0x10008	add x2, x0, x1
0x1000c	mov x3, #0x4000
0x10010	str x2, [x3]
0x10014	ret

Imagine our hypothetical CPU tries to execute this program without a TLB (or caches). We try to load the virtual address 0x10000 to try and get the first instruction. We do a page table walk starting at the physical address in TTBR0_EL1. This walk is going to require multiple memory accesses since we have multiple levels of page tables (usually 4.) This walk will cost roughly 400ns, which from the eyes of our CPU is extremely costly. And this was just to get the physical address for 0x10000, we haven’t even loaded that physical address to get the instruction yet! Once we do fetch the instruction after waiting ~100ns, we can finally execute one mov instruction. Now we try to load the address 0x10004 to get the next instruction. Time for another page table walk! Next, we’ll try to load the address 0x10008 and you get the idea. We will have to do a page table walk every time we try to fetch an instruction.

It is obvious that without caching these virtual to physical translations, our CPU will spend a majority of its time performing page table walks rather than executing the actual instructions.

baby steps

Let’s add the most simple TLB: one that caches the latest virtual to physical translation. Starting from the beginning of our previous program, we will try to load the virtual address 0x10000 and perform a page table walk. We will still have a ~400ns penalty for this first walk. But for our next load of 0x10004, we will first check our TLB and see that our we have the translation of this page already cached and use it. We have just shaved off ~400ns of memory accesses and we are blazing through our program now.

But we will run into slowdowns after executing the instruction at 0x10010. We perform a store operation to the virtual address 0x4000. This virtual page’s translation is not in our TLB, which means we will need to do a page table walk. We will overwrite the old 0x10000 to p entry in our TLB to 0x4000 to p2. But now when we try to fetch the instruction at 0x10014, we find that its translation is not in the cache, which means another page table walk. We can see with multiple pages in use, we are hitting slowdowns. How can we fix this?



a. add more entries

The most obvious solution is to just add more space to our TLB so we can store more entries. But more entries means more problems. We can’t have infinite entries in our TLB.

  • can’t have infinite entries, too much and we won’t find in reasonable time
  • which slot does an entry go into?
  • which entries deserve to leave? managing LRU is complicated
